# QA 计划

此技能为迭代、功能或单个故事生成结构化 QA 计划。它读取范围内的所有故事文件及其引用的 GDD，按测试类型对每个故事分类，并生成一份计划，明确开发者需要自动化测试什么、手动验证什么、冒烟测试范围是什么，以及何时需要引入试玩。

在迭代开始前运行此技能，使团队提前了解所需的测试工作。实现完成后才编写的测试计划是事后总结，而不是计划。

**输出：** `production/qa/qa-plan-[sprint-slug]-[date].md`

---

## 第 1 阶段：解析范围

**参数：** `$ARGUMENTS`（空白 = 通过 AskUserQuestion 询问用户）

根据参数确定范围：

- **`sprint`** — 读取 `production/sprints/` 中最新的文件，提取其中引用的每个故事文件路径。如果存在 `production/sprint-status.yaml`，将其作为主要故事列表，并以迭代计划补充故事元数据。
- **`feature: [system-name]`** — glob `production/epics/*/story-*.md`，筛选文件路径或标题包含系统名称的故事。同时检查该系统目录中的史诗索引文件（`EPIC.md`）。
- **`story: [path]`** — 验证路径存在，并加载该单个文件。
- **无参数** — 使用 `AskUserQuestion`：
  - “此 QA 计划的范围是什么？”
  - 选项：“当前迭代”、“指定功能（输入系统名称）”、“指定故事（输入路径）”、“完整史诗”

确定范围后，报告：“正在为 [范围] 中的 [N] 个故事构建 QA 计划。”

如果引用的故事文件路径不存在，将其标记为 MISSING，并继续处理剩余故事。不要因一个文件缺失而使整个计划失败。

---

## 第 2 阶段：加载输入

对每个范围内的故事文件，读取完整文件并提取：

- **故事标题**和故事 ID（来自文件名或标题）
- **故事类型**字段（如果文件头中存在，例如 `Type: Logic`）
- **验收标准** — 完整的编号或项目符号列表
- **实现文件** — “Files to Create / Modify”或类似章节中列出的文件
- **引擎说明** — 任何引擎 API 警告或版本特定说明
- **GDD 引用** — 引用的 GDD 路径
- **ADR 引用** — 引用的 ADR
- **估算** — 小时数或故事点（如果存在）
- **依赖项** — 此故事依赖的其他故事

读取故事后，一次性加载支持性上下文，而不是每个故事分别加载：

- `design/gdd/systems-index.md` — 了解系统优先级以及哪些 GDD 已获批准
- 对所有故事中引用的每个唯一 GDD：读取 **Acceptance Criteria**、**Formulas** 和 **Edge Cases** 章节。不要加载完整 GDD 文本。这三个章节包含可测试的需求、需要验证的数学公式，以及测试必须覆盖的边界条件。如果 GDD 缺少 Edge Cases 章节，按 GDD 记录：“未找到 Edge Cases 章节 — 边界情况覆盖范围将仅根据验收标准推断。”
- `docs/architecture/control-manifest.md` — 扫描自动化测试应防护的禁止模式（如果文件存在）

如果故事没有引用 GDD，将其记录为缺口，但不要阻止计划生成。故事将仅根据验收标准进行分类。

---

## 第 3 阶段：为每个故事分类

为每个故事分配故事类型：

- **如果故事头中已有 `Type:` 字段**：按原样接受。不要根据以下标准重新分类或验证 — 该类型由 lead-programmer 在创建故事时设定，具有权威性。按原样记录。
- **如果缺少 `Type:` 字段**：使用下表根据验收标准推断类型，并在报告中注明类型是推断的（而非声明的）。将其标记为缺口 — 故事应在实现开始前显式声明类型。

| 故事类型 | 分类指标 |
|---|---|
| **Logic** | 验收标准涉及计算、公式、数值阈值、状态转换、AI 决策、数据验证、增益或减益叠加、经济交易，或任何可测试的计算 |
| **Integration** | 标准涉及两个或更多系统交互、信号或事件跨系统边界传播、存档或读档往返、网络同步或持久化 |
| **Visual/Feel** | 标准涉及动画行为、VFX、着色器输出、“响应感”、感知时序、屏幕震动、粒子效果、音频同步或视觉反馈质量 |
| **UI** | 标准涉及菜单、HUD 元素、按钮、屏幕、对话框、物品栏面板、工具提示或任何面向玩家的界面元素 |
| **Config/Data** | 变更仅限于平衡调优值、数据文件或配置，不涉及新的代码逻辑 |

**混合故事**（例如同时添加公式和 UI 展示）：根据验收标准中实现风险最高的部分分配主要类型，并记录次要类型。Logic+Integration 或 Visual+UI 组合最常见。

完成所有故事分类后，在进入第 4 阶段之前先在对话中生成分类汇总表。这让用户能够了解测试将如何分配。

---

## 第 4 阶段：生成测试计划

组装完整的 QA 计划文档。使用以下结构：

````markdown
# QA 计划：[迭代/功能名称]
**日期**：[date]
**生成者**：/qa-plan
**范围**：[N 个故事，涉及 [N] 个系统]
**引擎**：[来自 .claude/docs/technical-preferences.md 的引擎名称，或“未配置”]
**迭代文件**：[适用时填写迭代计划路径]

---

2. 可以开始新游戏或新会话

5. 存档或读档循环完成且无数据丢失（如果存在存档系统）

## 定义完成 — 本迭代

只有满足以下全部条件，故事才算 DONE：

- [ ] 所有验收标准已验证 — 通过自动化测试结果，或带签核的书面手动证据（截图、视频或试玩记录）
- [ ] 所有 Logic 和 Integration 故事的测试文件已存在于指定路径
- [ ] 所有 Visual/Feel 和 UI 故事均存在手动证据文档
- [ ] 冒烟检查通过（QA 移交前运行 `/smoke-check sprint`）
- [ ] 未引入回归
- [ ] 已完成代码审查（通过 `/code-review` 或有记录的同行审查）
- [ ] 故事文件已更新为 `Status: Complete`（通过 `/story-done`）
````

生成内容时，使用第 2 阶段提取的实际故事标题、GDD 公式文本和验收标准。不要使用占位文本 — 每个测试条目都应反映这些具体故事的真实需求。

## 第 5 阶段：写入输出

在对话中展示完整计划（如果计划很长，可以展示摘要），然后使用 `AskUserQuestion` 一次询问以下两个问题：

```
question: "准备写入 QA 计划。请选择输出选项："
multiSelect: true
options:
  - "将 QA 计划写入 production/qa/qa-plan-[sprint-slug]-[date].md"
  - "同时将测试用例规格回填到每个故事文件的 ## QA Test Cases 章节（推荐 — 启用 /dev-story 和 /code-review 的可追溯性）"
```

如果选择“写入 QA 计划”：按生成内容准确写入计划文件 — 不要截断。

如果选择“同时回填故事文件”：对于范围内的每个 Logic 和 Integration 故事，编辑其路径对应的故事文件。找到 `## QA Test Cases` 章节，并将其内容替换为第 4 阶段为该故事生成的测试用例规格。如果故事没有 `## QA Test Cases` 章节，则在 `## Test Evidence` 之前追加该章节。对于 Visual/Feel 和 UI 故事，写入手动验证步骤而不是测试规格。

写入后：

“QA 计划已写入 `production/qa/qa-plan-[sprint-slug]-[date].md`。

后续步骤：
- 在迭代实现开始前与团队分享此计划
- 所有迭代故事实现完成后，运行 `/smoke-check sprint` 作为 QA 移交门禁 — 现在不要运行，必须等实现完成
- 对于 Logic/Integration 故事，在标记故事完成前创建列出路径中的测试文件
  — `/story-done` 会检查这些文件”

静默追加到 `production/session-state/active.md`（如果文件不存在则创建）：

```
<!-- QA-PLAN: [date] | System: [system/sprint identifier] | Plan written: production/qa/qa-plan-[identifier]-[date].md -->
```

## 协作协议

- **未经询问不得写入计划** — 第 5 阶段要求明确批准。
- **保守分类**：当故事在 Logic 和 Integration 之间存在歧义时，将其分类为 Integration — 它需要单元测试和集成测试。
- **不要发明测试用例**，测试用例必须有验收标准和 GDD 公式支持。如果 GDD 中缺少公式，应标记这一点，而不是猜测。
- **试玩要求仅供建议**：用户决定边界情况下的 Visual/Feel 故事是否需要试玩。标记该情况，不要强制要求。
- 无参数时使用 `AskUserQuestion` 选择范围。其余阶段保持非交互式 — 展示结果，然后只询问一次是否批准写入。
