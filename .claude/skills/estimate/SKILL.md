## Phase 1: 理解任务

从参数中读取任务描述。如果描述过于模糊而无法进行有意义的估算，请先询问澄清。

读取 CLAUDE.md 获取项目上下文：技术栈、编码标准、架构模式和任何估算指导原则。

读取 `design/gdd/` 中的相关设计文档（如果任务与记录的功能或系统相关）。

---

## Phase 2: 扫描受影响代码

识别需要更改的文件和模块：

- 评估复杂度（大小、依赖数量、圈复杂度）
- 识别与其他系统的集成点
- 检查受影响区域中的现有测试覆盖
- 从 `production/sprints/` 读取过去的迭代数据，以获取类似已完成任务和历史速度

## Phase 3: 分析复杂度因素

**代码复杂度：**
- 受影响文件中的代码行数
- 依赖关系数量和耦合程度
- 是否触及核心/引擎代码 vs 叶子/功能代码
- 是否可以遵循现有模式或需要新模式

**范围：**
- 涉及的系统数量
- 新代码 vs 修改现有代码
- 需要的新测试覆盖量
- 需要的数据迁移或配置更改

**风险：**
- 新技术或不熟悉的库
- 不清楚或模糊的需求
- 对未完成工作的依赖
- 跨系统集成复杂度
- 性能敏感性

## Phase 4: 生成估算

```markdown
## 任务估算：[任务名称]
生成时间：[日期]

### 任务描述
[用1-2句话清楚地重述任务]

### 复杂度评估

| 因素 | 评估 | 说明 |
|--------|-----------|-------|
| 受影响的系统 | [列表] | [核心、游戏玩法、UI等] |
| 可能修改的文件 | [数量] | [关键文件列在下面] |
| 新代码 vs 修改 | [比例] | |
| 集成点 | [数量] | [哪些系统交互] |
| 需要的测试覆盖 | [低 / 中 / 高] | |
| 可用的现有模式 | [是 / 部分 / 否] | |

**可能受影响的关键文件：**
- `[path/to/file1]` -- [此处发生了什么更改]

### 工作量估算

| 场景 | 天数 | 假设 |
|----------|------|------------|
| 乐观情况 | [X] | 一切顺利，无意外 |
| 预期情况 | [Y] | 正常速度，小问题，一轮评审 |
| 悲观情况 | [Z] | 出现重大未知问题，被阻塞一天 |

**推荐预算：[Y 天]**

### 置信度：[高 / 中 / 低]

[解释哪些因素驱动了此特定任务的置信度水平。]

### 风险因素

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|-----------|--------|------------|

### 依赖关系

| 依赖 | 状态 | 延迟时的影响 |
|-----------|--------|-------------------|

### 建议的分解

| # | 子任务 | 估算 | 说明 |
|---|----------|----------|-------|
| 1 | [研究 / 试点] | [X 天] | |
| 2 | [核心实现] | [X 天] | |
| 3 | [测试和验证] | [X 天] | |
| | **总计** | **[Y 天]** | |

### 说明和假设
- [影响估算的关键假设]
- [任何关于范围边界的警告]
```

输出估算结果并附带简短摘要：推荐预算、置信水平和最大的单一风险因素。

此技能是只读的 —— 不写入文件。结论：**COMPLETE** —— 估算已生成。

## Phase 5: 后续步骤

- 如果置信度为低：建议在承诺前进行时间盒试点（`/prototype`）。
- 如果任务超过 10 天：建议通过 `/create-stories` 拆分为更小的故事。
- 要安排任务：运行 `/sprint-plan update` 将其添加到下一个迭代。

### 指导原则

- 始终给出范围（乐观 / 预期 / 悲观），绝不给单一数字
- 推荐预算应为预期估算，而非乐观估算
- 四舍五入到半天增量 —— 以小时估算意味着对超过一天的任务存在虚假精度
- 不要静默填充估算 —— 明确指出风险，让团队决定
