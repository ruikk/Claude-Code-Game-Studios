# 项目阶段检测

本技能扫描你的项目以确定其当前开发阶段、产出物完整度，以及需要关注的缺口。在以下场景尤其有用：
- 接手一个现有项目
- 入职一个代码库
- 在里程碑前检查缺失项
- 理解"我们到哪了？"

---

## 工作流程

### 1. 扫描关键目录

分析项目结构和内容：

**设计文档**（`design/`）：
- 统计 `design/gdd/*.md` 中的 GDD 文件数量
- 检查是否存在 game-concept.md、game-pillars.md、systems-index.md
- 如果 systems-index.md 存在，统计系统总数与已设计系统数
- 分析完整度（概览、详细规则、边缘情况等）
- 统计 `design/narrative/` 中的叙事文档
- 统计 `design/levels/` 中的关卡设计

**源代码**（`src/`）：
- 统计源文件数量（与语言无关）
- 识别主要系统（含 5 个以上文件的目录）
- 检查是否存在 core/、gameplay/、ai/、networking/、ui/ 目录
- 估算代码行数（粗略规模）

**制作产出物**（`production/`）：
- 检查是否有活跃的迭代计划
- 查找里程碑定义
- 查找路线图文档

**原型**（`prototypes/`）：
- 统计原型目录数量
- 检查是否有 README（有文档与无文档）
- 评估原型是已归档还是活跃中

**架构文档**（`docs/architecture/`）：
- 统计 ADR（架构决策记录）数量
- 检查是否存在概览/索引文档

**测试**（`tests/`）：
- 统计测试文件数量
- 估算测试覆盖率（粗略启发式）

### 2. 分类项目阶段

基于扫描的产出物确定阶段。先检查 `production/stage.txt` —— 如果存在，使用其值（来自 `/gate-check` 的显式覆盖）。否则，使用以下启发式规则自动检测（从最先进的阶段向后检查）：

| 阶段 | 指标 |
|-------|-----------|
| **概念**（Concept） | 无游戏概念文档，处于头脑风暴阶段 |
| **系统设计**（Systems Design） | 游戏概念存在，系统索引缺失或不完整 |
| **技术搭建**（Technical Setup） | 系统索引存在，引擎未配置 |
| **预制作**（Pre-Production） | 引擎已配置，`src/` 少于 10 个源文件 |
| **制作**（Production） | `src/` 有 10 个以上源文件，活跃开发中 |
| **打磨**（Polish） | 仅显式设置（由 `/gate-check` 制作→打磨门禁设置） |
| **发布**（Release） | 仅显式设置（由 `/gate-check` 打磨→发布门禁设置） |

### 3. 协作式缺口识别

**不要**只是列出缺失的文件。相反，**提出澄清性问题**：

- "我看到战斗代码（`src/gameplay/combat/`）但没有 `design/gdd/combat-system.md`。这是先做了原型，还是我们应该补写文档？"
- "你有 15 个 ADR 但没有架构概览。需要我创建一个来帮助新贡献者吗？"
- "`production/` 中没有迭代计划。你是否在其他地方跟踪工作（Jira、Trello 等）？"
- "我找到游戏概念但没有系统索引。你是否已经将概念分解为单个系统，还是我们应该运行 `/map-systems`？"
- "原型目录有 3 个项目但没有 README。这些是实验，还是需要文档？"

### 4. 生成阶段报告

使用模板：`.claude/docs/templates/project-stage-report.md`

**报告结构**：
```markdown
# 项目阶段分析

**日期**：[日期]
**阶段**：[概念/系统设计/技术搭建/预制作/制作/打磨/发布]
**阶段置信度**：[PASS —— 清晰检测到 / CONCERNS —— 信号模糊 / FAIL —— 关键缺口阻塞进展]

## 完整度概览
- 设计：[X%]（[N] 篇文档，[缺口]）
- 代码：[X%]（[N] 个文件，[系统]）
- 架构：[X%]（[N] 个 ADR，[缺口]）
- 制作：[X%]（[状态]）
- 测试：[X%]（[覆盖率估算]）

## 已识别的缺口
1. [缺口描述 + 澄清问题]
2. [缺口描述 + 澄清问题]

## 推荐的下一步
[基于阶段和角色的优先级排序列表]
```

### 5. 角色过滤推荐（可选）

如果用户提供了角色参数（例如 `/project-stage-detect programmer`）：

**程序员**：
- 聚焦架构文档、测试覆盖率、缺失的 ADR
- 代码与文档的缺口

**设计师**：
- 聚焦 GDD 完整度、缺失的设计章节
- 原型文档

**制作人**：
- 聚焦迭代计划、里程碑跟踪、路线图
- 跨团队协调文档

**通用**（无角色）：
- 所有缺口的全局视角
- 跨领域的最高优先级条目

### 6. 写入前请求批准

**协作协议**：
```
我已分析你的项目。以下是我发现的：

[展示摘要]

已识别的缺口：
1. [缺口 1 + 问题]
2. [缺口 2 + 问题]

推荐的下一步：
- [优先级 1]
- [优先级 2]
- [优先级 3]

我可以将完整的阶段分析写入 production/project-stage-report.md 吗？
```

等待用户批准后再创建文件。

## 后续行动

生成报告后，建议相关的下一步：

- **有概念但无系统索引？** → 运行 `/map-systems` 分解为系统
- **缺少设计文档？** → `/reverse-document design src/[system]`
- **缺少架构文档？** → `/architecture-decision` 或 `/reverse-document architecture`
- **原型需要文档？** → `/reverse-document concept prototypes/[name]`
- **没有迭代计划？** → `/sprint-plan`
- **临近里程碑？** → `/milestone-review`

---

## 协作协议

本技能遵循协作设计原则：

1. **先提问**：询问缺口，不要假设
2. **提供选项**："需要我创建 X，还是在其他地方跟踪？"
3. **用户决定**：等待指引
4. **展示草稿**：显示报告摘要
5. **获得批准**："我可以写入 production/project-stage-report.md 吗？"

**绝不**默默写入文件。**始终**先展示发现并在创建产出物前询问。
