# 代理测试规范：analytics-engineer

## 代理摘要
- **领域**：遥测架构和事件模式设计、A/B 测试框架设计、玩家行为分析方法、分析仪表板规范、事件命名约定、数据管线设计（模式 → 摄取 → 仪表板）
- **不负责**：游戏中的事件跟踪实现（由适当的程序员负责）、基于分析结果作出的经济设计决策（economy-designer）、在线运营活动设计（live-ops-designer）
- **模型层级**：Sonnet
- **门禁 ID**：无；生成模式和测试设计；将实现交由程序员负责

## 测试用例

### 用例 1：领域内请求——教程事件跟踪设计
**输入**："为教程设计分析事件跟踪。我们想知道玩家在哪里流失，以及他们完成了哪些步骤。"
**预期行为**：
- 为每个教程步骤生成结构化事件模式，至少包含 `event_name`、`properties`（step_id、step_name、player_id、session_id、timestamp）和 `trigger_condition`（事件触发的确切时机——步骤开始、步骤完成、步骤跳过时）
- 包含漏斗完成事件和流失事件（例如玩家在某步骤期间退出时触发 `tutorial_step_abandoned`）
- 指定事件命名约定：使用 snake_case 并添加领域前缀（例如 `tutorial_step_started`、`tutorial_step_completed`、`tutorial_abandoned`）
- 不得生成实现代码——将实现标记为 [TO BE IMPLEMENTED BY PROGRAMMER]
- 输出为模式表或结构化列表，而非叙述性说明

### 用例 2：领域外请求——用代码实现事件跟踪
**输入**："事件模式已经设计完成，现在编写 GDScript 代码，在 Godot 教程场景中触发这些事件。"
**预期行为**：
- 不生成 GDScript 或任何实现代码
- 明确说明："游戏代码中的遥测实现由适当的程序员（gameplay-programmer 或 systems-programmer）负责；我提供事件模式和集成要求"
- 可选择生成集成规范：程序员正确实现所需的信息（事件名称、属性、触发时机、要使用的分析 SDK 或端点）

### 用例 3：领域边界——界面改动的 A/B 测试设计
**输入**："我们想对 HUD 的两个版本进行 A/B 测试：当前版本，以及只保留生命条的精简版本。请设计该测试。"
**预期行为**：
- 生成完整的 A/B 测试设计文档：
  - **假设**：精简 HUD 将通过降低界面认知负担来提高玩家参与度（以游玩时长衡量）
  - **主要指标**：每名玩家的平均游玩时长
  - **次要指标**：教程完成率、第 1 天留存率
  - **样本量**：基于预期效应量计算的估算值（或说明精确计算需要基线数据）——不得跳过该字段
  - **持续时间**：最短持续时间（例如“至少 2 周，以捕捉玩家每周行为模式”）
  - **随机化单位**：玩家 ID（而非会话 ID，以防玩家看到两个版本）
- 输出应组织为正式测试设计，而非想法项目符号列表

### 用例 4：冲突——A/B 测试玩家分群重叠
**输入**："我们同时运行两个 A/B 测试：测试 A（HUD 变体）影响所有玩家，测试 B（教程变体）也影响所有玩家。"
**预期行为**：
- 将重叠标记为互斥违规：如果两个测试影响同一玩家，其结果就会受到混杂——两个测试都无法得到干净数据
- 准确指出问题：同时参与两个测试的玩家会受到 HUD 与教程变体的交互影响，因此无法将结果差异归因于任何单一变量
- 提出解决方案：(a) 依次运行测试；(b) 将玩家群体拆分为互斥分群（50% 参与测试 A，50% 参与测试 B，0% 同时参与）；或 (c) 如果也关注交互效应，则采用析因设计（更复杂，需要更大样本）
- 不得建议在重叠群体中继续运行两个测试

### 用例 5：上下文传递——新事件与现有模式保持一致
**输入上下文**：现有事件模式使用 snake_case 格式的命名约定：`[domain]_[object]_[action]`。示例事件：`combat_enemy_killed`、`inventory_item_equipped`、`tutorial_step_completed`。
**输入**："为新的制作系统设计事件跟踪：玩家收集材料、打开制作菜单并制作物品。"
**预期行为**：
- 生成严格遵循给定模式命名约定的事件：`crafting_material_gathered`、`crafting_menu_opened`、`crafting_item_crafted`
- 不得创造其他命名模式（例如 `gatherMaterial`、`craftingOpened`），即使它看起来很自然
- 属性遵循与现有事件相同的结构：以 `player_id`、`session_id`、`timestamp` 作为标准字段；以领域特定字段（material_type、item_id、crafting_time_seconds）作为附加属性
- 输出明确说明正在遵循所提供的命名约定标准

## 协议合规性

- [ ] 保持在声明的领域内（事件模式设计、A/B 测试设计、分析方法）
- [ ] 将实现请求连同集成规范转交适当的程序员，而不是提供代码
- [ ] 生成完整的 A/B 测试设计（假设、指标、样本量、持续时间、随机化单位）——绝不残缺
- [ ] 将重叠 A/B 测试中的互斥违规标记为数据质量阻塞项
- [ ] 严格遵循给定的命名约定；不得创造替代约定

## 覆盖说明
- 用例 3（A/B 测试设计完整性）是质量门禁——不完整的测试设计会浪费实验预算
- 用例 4（互斥）是数据完整性测试——重叠测试会产生不可用的结果；必须发现这一问题
- 用例 5 是最重要的上下文感知测试；模式之间命名约定的偏移会导致仪表板失效
- 无自动化运行器；请手动审查或通过 `/skill-test` 审查
