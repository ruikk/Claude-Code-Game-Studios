# 反向文档工作流示例

## 场景
开发者构建了一个可运行的技能树系统，但从未编写设计文档。
代码位于 `src/gameplay/skills/`，但 `design/gdd/` 中没有 skill-system.md。

---

## 会话记录

**用户：**
```
我在 src/gameplay/skills/ 中有一个可以运行的技能树系统，大约有 1200 行
代码。我从未写过设计文档。我们可以根据实现创建一份吗？
```

**Game-Designer（读取并分析代码）：**
```
我已经分析了你的技能树实现。以下是我的发现：

结构：
- 3 个技能树：Combat、Survival、Tech
- 每棵树 5 个层级（通过等级 + 前置条件解锁）
- 总计 45 个技能（每棵树 15 个）
- 消耗：技能点（每级 1 点，可花费金币重置）

机制：
- 被动技能（属性加成）
- 主动技能（带冷却时间的能力）
- 协同加成（第 4 层及以上可跨树解锁）

实现细节：
- 数据驱动（`assets/data/skills/` 中的 JSON 文件）
- 兼容存档（技能状态已序列化）
- UI 显示锁定/已解锁/可用状态

在起草设计文档前的问题：

1. **设计意图：**3 棵树的结构是用于表示玩家原型
   （fighter/survivor/engineer），还是用于提供玩法风格的灵活性？

2. **重置成本：**重置需要金币，这是为了：
   - 限制频繁重置（要求玩家坚持构筑）？
   - 创造金币消耗点（经济平衡）？
   - 还是应该免费（鼓励实验）？

3. **协同系统：**跨树协同出现在第 4 层。这是：
   - 有意设计的（在后期奖励混合构筑）？
   - 还是涌现的（意外形成混合流派）？

4. **平衡理念：**我看到有些技能明显更强（第 5 层被动技能提供 +50% 伤害）。这是：
   - 强力幻想（后期应该感觉很强）？
   - 还是不平衡（需要调节）？
```

**用户：**
```
问得好！以下是我的意图：

1. 是的，3 棵树代表不同原型，但我希望保留灵活性
2. 重置应该便宜，我希望鼓励实验
3. 协同是有意设计的，混合构筑是一项功能
4. 是的，第 5 层应该很强，但 +50% 可能太高了
```

**Game-Designer：**
```
完美，这明确了构想。我来起草设计文档：

[展示 design/gdd/skill-system.md 的草稿]

章节：
1. 概述（3 棵树的系统、适合混合构筑、鼓励重置）
2. 设计支柱：
   - 原型清晰度（每棵树都有自己的身份）
   - 构筑灵活性（不锁定、重置便宜）
   - 协同奖励（跨树组合可行）
3. 详细设计（树结构、解锁规则、重置）
4. 平衡框架（层级强度曲线、协同限制）
5. 边界情况（战斗中重置？技能达到上限？上限？）
6. 依赖项（UI、存档系统、教程）
7. 验收标准（所有技能树都可行、10+ 种混合构筑、清晰的工具提示）
8. 待解决问题：
   - 重置成本应随等级增长还是保持固定？
   - 第 5 层伤害加成：调整为 +30% 还是保持 +50%？

**可以将此内容写入 design/gdd/skill-system.md 吗？**
```

**用户：**
```
可以，写入吧。但请将第 5 层调整为 +30%，并让重置成本随等级增长。
```

**Game-Designer：**
```
✅ 已写入 design/gdd/skill-system.md
✅ 已标记为 [REVERSE-DOCUMENTED FROM IMPLEMENTATION]
✅ 已添加 TODO：在 assets/data/skills/combat-tree.json 中将第 5 层被动技能更新为 +30%
✅ 已添加 TODO：实现随等级增长的重置成本公式

后续步骤：
- 运行 /balance-check 验证技能树成长曲线？
- 创建 ADR，记录为何采用 3 棵树而不是 5 棵？
- 更新教程以解释混合协同？
```

---

## 关键观察

1. **代理提出了澄清问题** - 不只是描述代码
2. **区分了意图与实现** - 用户纠正了“意外”的不平衡
3. **设计文档记录了“为什么”** - 不只是“代码做什么”
4. **识别出缺失部分** - 代码中没有覆盖边界情况
5. **标记了后续工作** - 平衡调节、ADR、教程

## 结果

设计文档现在已经存在，既**符合现实**，又记录了**预期构想**。今后的修改都会参考此文档，新团队成员也能理解这些决策背后的*原因*。
